# 운영 안내

## 실행 환경

GitHub Actions (public repo). Vercel 무료 티어는 **불가**하다 — cron 이 하루 1회로 제한되고, 파일시스템이 휘발이라 SQLite 상태가 매 실행 사라진다. 상태가 사라지면 알림 폭탄을 내거나 아무것도 안 보내거나 둘 중 하나다.

| 워크플로 | 주기 (KST) | UTC cron |
|---|---|---|
| `check.yml` | 24시간, 30분마다 | `*/30 * * * *` |
| `digest.yml` | 매일 08:00 | `0 23 * * *` |

`--check` 는 종일 실행이라 시간대 변환이 필요 없다. **`--digest` 만 주의**하면 된다: UTC 23시가 KST 다음 날 08시다.

GitHub cron 은 부하에 따라 **최대 30분 지연**될 수 있다. 마감일 기준 알림이라 문제되지 않는다.

### HANDOFF §11.5 와의 차이 (의도된 변경)

명세서는 "평일 09~19시 제한"을 학교 서버 배려로 명시했다. 24시간 운영은 여기서 벗어나지만 **총 요청량은 오히려 비슷하다.**

| | 실행/일 | 목록 요청/일 | 주간 |
|---|---|---|---|
| 명세서안 (평일 10분) | 66 | 528 (평일만) | 약 2,640 |
| 현재 (24h 30분) | 48 | 384 (매일) | 약 2,688 |

요청 간격 1.5초와 병렬 금지는 그대로다. 새벽은 학교 서버가 한가한 시간이라 부하 관점에서 불리하지 않다. **이 근거를 모르고 되돌리지 말 것.**

## 시크릿

| 이름 | 필수 | 비고 |
|---|---|---|
| `GEMINI_API_KEY` | ✅ | **AI Studio 키**. 무료 한도는 여기서만 나온다 |
| `TELEGRAM_BOT_TOKEN` | ✅ | |
| `TELEGRAM_CHAT_ID` | ✅ | 채널은 `-100…` 형태. 앞자리를 빼면 조용히 실패한다 |
| `CUK_HEALTHCHECK_URL` | 권장 | `--check` 용 healthchecks.io ping URL |
| `CUK_HEALTHCHECK_DIGEST_URL` | 권장 | `--digest` 용 (별도 모니터) |

`CUK_VERTEX_CREDENTIALS` 는 **운영에 등록하지 않는다.** Vertex 는 과금 경로이며 테스트 전용이다. 모든 실행이 시작 시 `자격증명: ...` 을 출력하므로 어느 쪽으로 도는지 항상 보인다.

## 최초 기동 순서

**순서를 어기면 알림 폭탄이 난다.**

1. 시크릿 등록
2. `--backfill` 1회 실행 (`workflow_dispatch` 로 수동) — 기존 공지를 읽음 처리
3. 스케줄 활성화 확인
4. 채널 테스트 메시지 삭제

# 장애 대응

## 핵심 원칙

**침묵은 정상과 구분되지 않는다.** 봇이 죽어도 채널은 조용할 뿐이고, 이는 "새 공지 없는 날"과 똑같이 보인다. 그래서 감지 장치를 두 겹으로 둔다.

| 층 | 담당 | 신호 |
|---|---|---|
| 외부 (healthchecks.io) | "죽었는지" | ping 끊기면 이메일 |
| 내부 (`crawl_log`) | "왜 죽었는지" | 게시판별 실패 이력, git 히스토리만큼 보존 |
| 채널 | "사용자가 눈치채는지" | 매일 08:00 메시지 부재 |

healthchecks 무료 플랜은 로그를 100건만 보존한다(30분 주기 = 약 2일). 경보 자체는 로그와 무관하므로 문제되지 않으며, 장기 추적은 `crawl_log` 가 맡는다.

## 유형별 조치

### 아침 메시지가 안 온다

가장 흔한 실제 장애 신호다.

1. GitHub Actions → 워크플로 실행 이력 확인
2. **60일 무활동으로 스케줄이 꺼졌는가?** — DB 커밋이 매 실행 쌓이므로 보통 발생하지 않지만, 봇이 오래 멈춰 있었다면 연쇄적으로 꺼질 수 있다. 수동 실행으로 되살린다
3. 실패했다면 로그에서 `자격증명:` 줄부터 확인 — 시크릿 만료가 흔한 원인

### "게시판 수집 실패" 알림이 왔다

같은 게시판이 3회 연속 실패하면 채널로 1회 통보된다(복구되면 자동 해제).

```bash
python -m cuk_bot --status          # 게시판별 실패 이력
python tools/m1_probe.py --board <id> --diagnose
```

`--diagnose` 는 본문 후보 컨테이너를 다시 순위 매긴다. 학교가 마크업을 바꿨다면 여기서 새 셀렉터가 보인다. `cuk_bot/parser.py` 의 `BODY_SELECTOR` 를 고치고 `docs/M1_RESULT.md` 를 갱신한다.

### "판정 없이 전달" 알림이 계속 온다

무료 한도가 모두 소진된 상태다. 정상 동작이며 데이터 손실은 없다.

```bash
python -m cuk_bot --status          # 모델별 잔여 확인
python -m cuk_bot --reextract       # 한도 회복 후 재판정 + 리마인더 예약
```

한도가 아니라 키 문제라면 `--status` 의 `자격증명:` 줄이 알려준다.

### 알림이 안 나간 것 같다

발송 실패분은 `outbox` 에 남아 다음 실행에서 자동 재시도된다(최대 5회).

```bash
python -m cuk_bot --status          # 미발송: 재시도 대기 N건, 재시도 포기 M건
```

"재시도 포기"가 있으면 텔레그램 설정을 확인한다. **메시지는 삭제되지 않으므로** 원인 해결 후 재시도하면 살아난다.

### 판정 규칙을 바꿨다

`normalize()` 의 규칙(마감 만료, 신뢰도 상한 등)을 고치면 **이미 저장된 판정은 낡은 채로 남는다.** 재추출은 이미 받은 답에 다시 돈을 내는 셈이라, 저장해 둔 모델 원본 응답으로 규칙만 다시 적용한다.

```bash
python -m cuk_bot --renormalize     # API 호출 없음
```

`--status` 가 낡은 판정 건수를 알려준다. 원본 응답은 `payload.raw` 에 보존되므로 규칙을 되돌려도 복구된다.

### DB가 깨졌거나 사라졌다

레포 히스토리가 곧 백업이다.

```bash
git log --oneline -- cuk_notices.db
git checkout <sha> -- cuk_notices.db
```

복구 불가능하면 **반드시 `--backfill` 을 먼저** 돌린다. 안 하면 수백 건이 한꺼번에 나간다. 단 예약돼 있던 리마인더는 사라지므로 채널에 안내한다.

### 학교에서 차단하거나 문의가 왔다

HANDOFF §13: **즉시 중단하고 의뢰인에게 보고한다.** 우회하지 않는다.

GitHub → Actions → 해당 워크플로 → `⋯` → Disable workflow

User-Agent 에 연락 이메일이 들어 있어(`CUK_CONTACT_EMAIL`) 학교 전산팀이 차단 대신 문의를 보내올 수 있다.

## 비용

운영은 무료 티어(AI Studio)만 쓴다. Vertex 테스트 프로젝트의 잔여 크레딧은 **API 로 조회할 수 없어** 콘솔에서 확인해야 한다(결제 → 크레딧). 대신 `--status` 가 우리가 쓴 토큰으로 예상 비용을 추정해 보여준다 — 단가표는 수동 관리라 참고용이다.

콘솔에 월 $1 예산 알림을 걸어두길 권한다. 예산은 Budget API 로도 만들 수 있지만 서비스 계정에 결제 계정 전체 관리 권한이 필요해, 알림봇에 붙일 권한이 아니다.
